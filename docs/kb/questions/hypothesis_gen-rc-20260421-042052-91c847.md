# Stage 08: Hypothesis Gen

# Core Ideas

## Idea 1: Phase-aware serving with queue isolation
- One-sentence claim: 在分布式大模型推理中，按 **prefill/decode 两阶段** 分离调度，并结合长短请求队列隔离，比固定并行策略更能稳定降低混合负载下的尾延迟。
- Core novelty: 不是只做静态 TP/PP 调优，而是利用 prefill 计算密集、decode 内存/通信敏感的差异，动态切换执行策略并避免长短请求互相阻塞。
- Why it matters: 真实线上推理的主要损失往往来自异构请求干扰和 phase mismatch，这一方法无需改模型即可直接提升 goodput 和 SLA 达成率。
- Minimal validation plan: 在 vLLM/TGI 上实现 prefill/decode 分离队列 + 简单 phase-aware 策略切换，与固定并行/固定 batching 基线比较，在混合 prompt/output 长度和 bursty trace 下测 p95 latency、goodput、GPU 利用率。
- Key risk: 收益可能主要来自简单队列隔离而非 phase-aware 并行切换，且额外调度复杂度可能导致吞吐碎片化。

## Idea 2: Deployment-aware distillation for shardable inference
- One-sentence claim: 若蒸馏目标显式约束 **KV footprint、跨 shard 激活可压缩性和边界通信代理指标**，则学生模型能在保持质量基本不变时显著降低分布式推理成本。
- Core novelty: 将蒸馏目标从“逼近 teacher 输出”扩展到“为分布式 serving 友好而训练”，直接优化 shard 边界状态和通信/内存瓶颈，而非只追求小模型精度。
- Why it matters: 现有压缩方法常只降低 FLOPs，却未必降低真实服务成本；若能让模型天生更易切分和缓存，可同时减少显存压力、通信量和延迟。
- Minimal validation plan: 选一个中小型 teacher-student 组合，加入边界表示压缩/KV 约束的蒸馏损失，在虚拟 2-way shard 或真实 2–4 GPU 部署中，对比标准蒸馏的通信量、KV 占用、p95 latency 与任务质量。
- Key risk: 通信代理指标的改善可能无法转化为端到端时延收益，或质量下降/fallback 增加抵消系统收益。

## Idea 3: Stress protocol instead of static benchmark
- One-sentence claim: 许多分布式推理优化在静态 benchmark 上有效，但在 **请求长度异构、突发流量、缓存压力和异构硬件** 条件下会发生明显性能排名翻转，因此应以 stress protocol 而非单一基准评估方法。
- Core novelty: 不做“统一排行榜”，而是设计一组能系统扰动 workload 和 hardware topology 的场景协议，用排名稳定性和 Pareto 前沿变化来衡量方法是否真正鲁棒。
- Why it matters: 如果评测协议本身忽略真实部署扰动，系统论文很容易对某一固定负载过拟合，导致结论无法指导生产环境中的分布式推理优化。
- Minimal validation plan: 选 3–4 类代表性方法（固定并行、Idea 1 调度、KV/cache 优化、压缩模型），在场景矩阵中测试其 throughput、p95/p99 latency、memory、interconnect traffic，并报告不同场景下的排名相关性。
- Key risk: 若方法排序在多数场景下基本稳定，则 stress protocol 的新增信息有限，贡献会退化为“更完整的 benchmark”而非新的研究发现。

## Hypothesis 1: Workload-aware phase switching beats static model-centric optimization

### Claim
For distributed LLM inference, **request heterogeneity and phase mismatch (prefill vs. decode)** are a larger source of end-to-end inefficiency than raw model size alone; therefore, **phase-aware scheduling with workload shaping** will outperform fixed parallelism or purely model-centric optimization.

### Why this survives synthesis
- **Innovator’s strongest idea:** phase-oscillating / phase-sensitive parallelism.
- **Pragmatist’s feasible version:** start with **prefill/decode separation**, not full token-by-token oscillation.
- **Contrarian correction:** the main bottleneck may be **heterogeneous workloads and scheduling failure**, not just model size or FLOPs.

### Rationale
Most distributed inference results are averaged over stable workloads, but real serving is dominated by:
- long/short request interference,
- decode memory-boundedness,
- tail latency,
- batching instability.

A practical but novel hypothesis is that the biggest gains come from **combining phase-aware execution with workload-aware routing/isolation**:
- prefill and decode use different strategies,
- long and short requests are separated or prioritized differently,
- scheduling is SLA-aware.

This is stronger than “prefill/decode differ” because it explicitly claims **system gains come more from matching workload shape than from static model optimization alone**.

### Measurable prediction
Against the best static serving baseline (fixed TP/PP or fixed batching policy), a workload-aware phase scheduler should achieve on mixed-length workloads:
- **p95 latency reduction ≥ 15%**
- **goodput (SLA-satisfying throughput) increase ≥ 10%**
- with no more than **5% loss in average throughput** in the worst case.

A stronger comparison:
- versus a model-centric baseline that only applies compression or parallel tuning, the scheduler should still improve **p95 latency by ≥ 10%** under heterogeneous workloads.

### Failure condition
Reject if any of the following hold:
1. Across mixed workloads, p95 latency gain is **< 5%**;
2. Gains appear only on synthetic balanced loads, but disappear on long-tail length distributions;
3. Queue isolation / phase switching causes enough fragmentation that goodput does not improve.

### Feasibility
High. Can be tested with:
- 1–4 GPUs,
- vLLM/TGI-style serving stack,
- synthetic or replayed request traces,
- no model training required.

### Unresolved disagreement
- **Innovator** would push toward finer-grained token-phase oscillation.
- **Pragmatist** prefers the safer prefill/decode split.
- **Contrarian** questions whether parallel-strategy switching matters as much as simple queue shaping and SLA isolation.  
So the real disagreement is: **is the gain coming from smarter parallelism, or mostly from better workload segregation?**

## Hypothesis 2: Deployment-aware distillation helps only if it improves system bottlenecks without increasing service-chain complexity

### Claim
A student model distilled with **explicit deployment-aware objectives**—especially shard-boundary compressibility / KV footprint / communication proxies—can reduce distributed inference cost **only when evaluated at the service level**, including fallback and task-completion overhead; otherwise, compression may merely shift complexity rather than reduce it.

### Why this survives synthesis
- **Innovator’s strongest novel contribution:** “shardability-aware” or boundary-consistent distillation.
- **Pragmatist’s feasibility filter:** use small-scale students and proxy losses.
- **Contrarian safeguard:** do **not** assume smaller/faster token generation means lower real service cost.

### Rationale
This hypothesis keeps the most original training-time idea: teach a model to be easier to partition and serve, not just to mimic logits. But it directly addresses the contrarian concern that compressed models can:
- lower answer quality,
- require longer outputs,
- trigger fallback to larger models,
- complicate routing.

So the real research question is not “does deployment-aware distillation lower perplexity under compression?” but:

> **Does it lower end-to-end distributed serving cost without increasing fallback or task-completion cost?**

This framing is both more novel and more honest than standard compression claims.

### Measurable prediction
Compared with standard distillation at the same student size, deployment-aware distillation should achieve:
- **cross-shard activation / communication proxy reduction ≥ 15%**
- **p95 serving latency reduction ≥ 10%**
- **GPU memory or KV-related footprint reduction ≥ 10%**
- while causing **task quality degradation ≤ 2%** or **fallback-rate increase ≤ 5% relative**
