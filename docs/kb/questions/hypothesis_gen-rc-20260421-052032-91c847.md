# Stage 08: Hypothesis Gen

# Core Ideas

## Idea 1: Phase-aware serving with queue isolation
- One-sentence claim: 在分布式大模型推理中，按 **prefill/decode 两阶段** 分离调度，并结合长短请求队列隔离，比固定并行策略更能稳定降低混合负载下的尾延迟。
- Core novelty: 不是只做静态 TP/PP 调优，而是利用 prefill 计算密集、decode 内存/通信敏感的差异，动态切换执行策略并避免长短请求互相阻塞。
- Why it matters: 真实线上推理的主要损失往往来自异构请求干扰和 phase mismatch，这一方法无需改模型即可直接提升 goodput 和 SLA 达成率。
- Minimal validation plan: 在 vLLM/TGI 上实现 prefill/decode 分离队列 + 简单 phase-aware 策略切换，与固定并行/固定 batching 基线比较，在混合 prompt/output 长度和 bursty trace 下测 p95 latency、goodput、GPU 利用率。
- Key risk: 收益可能主要来自简单队列隔离而非 phase-aware 并行切换，且额外调度复杂度可能导致吞吐碎片化。

## Idea 2: Deployment-aware distillation for shardable inference
- One-sentence claim: 若蒸馏目标显式约束 **KV footprint、跨 shard 激活可压缩性和边界通信代理指标**，则学生模型能在保持质量基本不变时显著降低分布式推理成本。
- Core novelty: 将蒸馏目标从“逼近 teacher 输出”扩展到“为分布式 serving 友好而训练”，直接优化 shard 边界状态和通信/内存瓶颈，而非只追求小模型精度。
- Why it matters: 现有压缩方法常只降低 FLOPs，却未必降低真实服务成本；若能让模型天生更易切分和缓存，可同时减少显存压力、通信量和延迟。
- Minimal validation plan: 选一个中小型 teacher-student 组合，加入边界表示压缩/KV 约束的蒸馏损失，在虚拟 2-way shard 或真实 2–4 GPU 部署中，对比标准蒸馏的通信量、KV 占用、p95 latency 与任务质量。
- Key risk: 通信代理指标的改善可能无法转化为端到端时延收益，或质量下降/fallback 增加抵消系统收益。

## Idea 3: Stress protocol instead of static benchmark
- One-sentence claim: 许多分布式推理优化在静态 benchmark 上有效，但在 **请求长度异构、突发流量、缓存压力和异构硬件** 条件下会发生明显性能排名翻转，因此应以 stress protocol 而非单一基准评估方法。
- Core novelty: 不做“统一排行榜”，而是设计一组能系统扰动 workload 和 hardware topology 的场景协议，用排名稳定性和 Pareto 前沿变化来衡量方法是否真正鲁棒。
- Why it matters: 如果评测协议本身忽略真实部署扰动，系统论文很容易对某一固定负载过拟合，导致结论无法指导生产环境中的分布式推理优化。
- Minimal validation plan: 选 3–4 类代表性方法（固定并行、Idea 1 调度、KV/cache 优化、压缩模型），在场景矩阵中测试其 throughput、p95/p99 latency、memory、interconnect traffic，并报告不同场景下的排名相关性。
- Key risk: 若方法排序在多数场景下基本稳定，则 stress protocol 的新增信息有限，贡献会退化为“更完整的 benchmark”而非新的研究发现。

# Core Ideas

## Idea 1: Phase-aware prefill/decode switching with low-cost repartition
- Problem gap: Existing distributed LLM inference typically uses a fixed parallelism plan, but prefill and decode have very different bottlenecks. Prior work and surveys do not provide a concrete, inference-specific method for deciding when dynamic switching is worth the repartition cost under real mixed workloads.
- Core idea: Build a runtime that treats prefill and decode as two execution phases with separate optimal plans: e.g., tensor-parallel or high-batch execution for prefill, then switch to a decode-optimized plan with smaller parallel groups, different batch policy, or different KV placement. Add a lightweight decision rule that switches only when predicted remaining decode time exceeds repartition overhead, using prompt length, active batch size, and KV-cache size as features.
- Why it is new: The novelty is not just “dynamic scheduling,” but explicit phase-aware repartition with a profitability gate and a workload phase diagram showing when switching beats the best fixed strategy. This is stronger than obvious baselines like fixed tensor parallelism, fixed pipeline parallelism, or static continuous batching.
- Why it is feasible now: Open-source serving stacks already expose enough hooks for prototype implementation, including vLLM, TensorRT-LLM, and DeepSpeed-Inference. On 2–4 GPUs, or even on 1 GPU with simulated communication delays, a student can evaluate the key tradeoff because the main question is switching overhead vs latency gain, not giant-model training.
- Minimal experiment: Use ShareGPT-style request traces plus synthetic mixes of prompt lengths {128, 512, 2k, 8k} and output lengths {32, 128, 512}. Start with Llama-2-7B/13B or Qwen2.5-7B-Instruct in vLLM; first implementation step is to add two execution modes and a per-request switch trigger at prefill completion.
- Strong baselines: Best fixed tensor-parallel plan; best fixed pipeline-parallel or hybrid plan; continuous batching without repartition; “never switch” oracle chosen separately for short/long prompts.
- Expected win: Lower p95 latency and time-to-first-token on long-prompt mixed workloads, with throughput increasing under load; target is p95 latency down and throughput up relative to the best fixed strategy, while automatically degenerating to no-switch on short prompts.
- Main risk: Repartition overhead or KV migration cost may dominate, especially on short prompts or low concurrency. The method may also be brittle if runtime prediction of remaining decode cost is inaccurate.
- 2-week MVP: Implement a two-mode executor in vLLM or a simulator: mode A for prefill-friendly large batches, mode B for decode-friendly smaller parallel groups. Use a threshold rule based on prompt length and expected output length to decide switching, and report p50/p95 latency, throughput, and switch overhead on synthetic traces.

## Idea 2: Deployment-aware distillation for communication- and KV-efficient distributed serving
- Problem gap: Compression and distillation are widely studied for accuracy/size tradeoffs, but there is little guidance on whether a distilled model actually improves distributed inference end-to-end. Existing work rarely optimizes student models for communication volume, KV-cache footprint, or partition-friendly execution.
- Core idea: Distill a student model with an additional serving-aware objective that penalizes cross-shard activation size and KV-cache growth while preserving next-token quality. Concretely, during teacher-student distillation, add losses on intermediate representations selected at intended shard boundaries, plus regularization for smaller KV norms/low-rank KV projections so the student is explicitly easier to partition and cheaper to serve.
- Why it is new: Standard KD optimizes task accuracy or logit matching; this idea optimizes for distributed execution properties that affect real serving cost. The key difference from obvious baselines is evaluating the student not only against a teacher and a vanilla KD student, but also against a “do not distribute” baseline such as quantized teacher or smaller quantized model on one device.
- Why it is feasible now: Small-to-mid-size open models can be distilled with modest compute, and shard-boundary communication/KV metrics can be measured directly in existing inference frameworks. This does not require training frontier models; a 1B–3B student distilled from a 7B teacher is enough to test whether serving-aware objectives translate into lower latency/cost.
- Minimal experiment: Use WikiText-103 or C4 slices for language modeling distillation and evaluate on LongBench or Needle-in-a-Haystack-style long-context subsets plus ShareGPT replay traces. Start with a Llama/Qwen teacher around 7B and a 1.5B–3B student; first implementation step is to add a boundary feature-matching loss at one or two planned partition layers and log per-token KV memory plus activation bytes transfer

# Final Hypothesis 1  
## **相位感知的动态执行策略（prefill/decode 分治，必要时重分片）优于任何固定并行策略，但其收益只在特定 workload 区域成立**

### Rationale
这是 innovator 的 “phase-switch dynamic repartition” 与 pragmatist 的 “阶段感知自适应并行” 的强结合，也是最直接面向分布式推理本体的问题。  
同时吸收 contrarian 的批评：**不存在普适最优策略**，因此假设不应写成“动态一定更好”，而应写成**在长 prompt、混合负载、decode 延迟敏感场景中更好；在短 prompt 或低并发场景可能无收益甚至负收益**。

核心思想：
- prefill 与 decode 的瓶颈不同，固定切法通常二者取其一而失其一；
- 但动态切换的额外重排成本可能吞噬收益；
- 所以研究重点不是证明“动态最好”，而是找出**收益边界条件**。

### Measurable prediction
在 2–4 GPU 或单卡虚拟多卡模拟下，对长短混合请求负载：

- 相比最佳固定策略，**phase-aware 策略**可使  
  - p95 latency 降低 **10%–20%**
  - throughput 提升 **5%–15%**
- 在 **长 prompt（≥1k）+ 中短 decode** 场景，若允许 prefill/decode 切换策略或重分片，  
  - 总推理时间下降 **≥ 12%**
  - 重分片/策略切换开销占总时间 **< 8%**
- 在 **短 prompt（≤256）** 场景，最优策略应自动退化为固定策略，否则说明方法不稳健。

### Failure condition
若出现以下任一，则该假设失败：
1. 相比最佳固定 baseline，p95 latency 改善 **< 5%**
2. throughput 无显著提升，或下降 **> 5%**
3. 动态切换开销在主要受益场景中占比 **> 12%**
4. 在短 prompt 场景不能自动退化，反而带来 **> 3%** 额外开销

### Unresolved disagreement
- **Innovator / pragmatist** 倾向认为动态分治是自然下一步；
- **Contrarian** 认为很多情况下最佳答案可能不是“更动态的分布式”，而是**避免进入复杂分布式路径**。  
因此这里仍有未决问题：  
**动态分治究竟是主路线，还是仅对少数长上下文高端请求成立的特例优化？**

# Final Hypothesis 2  
## **“部署感知压缩/蒸馏”只有在显式优化通信、KV-cache 与 fallback 风险时，才会转化为真实分布式收益；普通 accuracy-only 压缩未必优于去分布式化基线**

### Rationale
这是对 innovator 的 “反分布式蒸馏 / shardability distillation” 的保留，但加入 contrarian 的关键修正：  
**不能把蒸馏默认成系统收益，必须和两类基线比较：**
1. 普通 accuracy-only distillation
2. 不做分布式优化、但采用量化/缓存/路由的“去分布式化”方案

也就是说，最终假设不是“蒸馏会更好”，而是更严格的：
> 只有当蒸馏目标显式纳入分片边界压缩性、KV-cache footprint、通信量、甚至 fallback/升级大模型概率时，压缩才会真正改善分布式服务。

这保留了最有新意的研究点，也回应了 contrarian 对“压缩收益被系统现实吞噬”的担忧。

### Measurable prediction
对小 student 模型做轻量蒸馏或单卡原型验证时：

- 相比普通 KD student，**部署感知 student** 在相近质量下应实现：
  - 跨边界激活/通信压缩率提升 **≥ 1.3×**
  - 分布式推理吞吐提升 **≥ 10%**
  - 显存或 KV 占用下降 **≥ 15%**
- 且在任务质量上：
  - perplexity 或小样本任务精度下降不超过 **1%–3%**
- 更关键的是，与 **“teacher 量化版 + 去分布式化 serving”** 比较时，部署感知 student 至少在一个核心系统指标上稳定占优：
  - p95 latency
  - cost per token
  - fallback rate / route escalation rate

### Failure condition
若出现以下任一，则该假设失败：
1. 相比普通 KD，系统收益 **< 5%**
2. 精度损失 **> 3%–5%**
3. 压缩后的 student 在真实 serving trace 下，因 fallback/补偿导致总成本不低于 teacher 量化版
4. 所谓“部署感知目标”只能改善 proxy 指标，不能转化为端到端收益

### Unresolved disagreement
- **Innovator** 认为把“可分片执行性”蒸馏进模型是一个新主线；
- **Pragmatist** 认可，但担心训练复杂度和验证周期；
- **Contrarian** 则质疑：很多最优收益也许根本不来自“更适合分布式的模型”，而来自**尽量不分布式**。  
因此未决分歧是：  
**deployment-aware compression 是分布式推理的新核心，还是只是服务于去分布式化的一种手段？**

# Final Hypothesis 3  
## **轻量级在线控制器应优先做“路径选择”而非“局部调参”：最优收益可能来自决定何时避免分布式，而不只是动态调 batch/并行度**

### Rationale
这是对 innovator 的 “短时反事实 replay 控制器” 和 pragmatist 的 “轻量在线控制器” 的升级版，也吸收了 contrarian 的最强观点：  
**上层服务策略和流量整形，可能比底层并行优化更重要。**

因此最终版本不把控制器限定为：
- 调 batch size
- 调 continuous batching 阈值
- 调 precision

而是明确提出控制器首先应做一个更高价值的决策：
> **这个请求是否值得进入分布式路径？**

候选动作包括：
- 单机/低并行 vs 分布式执行
- prefill/decode 分离与否
- 是否启用更激进缓存/低精度
- 是否优先短请求
- 是否延迟、降级、或路由到另一服务层

这比单纯调参更符合现实系统，也直接回应了 “去分布式化” 论点。

### Measurable prediction
在合成或回放的多租户 trace 上，相比最佳静态配置与“仅局部调参控制器”：

- **反事实 replay / MPC 风格的轻量控制器** 可实现：
  - p95 latency 降低 **≥ 15%**
  - SLA violation rate 降低 **≥ 15%**
  - OOM 或显存超阈事件减少 **≥ 30%**
- 且相较于只调 batch/并行度的控制器，  
  **加入“路径选择（是否进入分布式）”后** 的收益应额外增加：
  - p95 latency 再改善 **≥ 5%**
  - 或 cost per token 再下降 **≥ 5%**
- throughput 损失不超过 **3%–5%**

### Failure condition
若以下任一成立，则拒绝该假设：
1. 相比最佳静态策略，p95 latency 改善 **< 8%**
2. throughput 下降 **> 5%**
3. “路径选择型控制器”并未显著优于“仅局部调参控制器”
4. 不同 workload trace 下结果极不稳定，在多数情况下无法优于简单规则基线

### Unresolved disagreement
- **Pragmatist** 认为轻量控制器很适合作为低风险主线；
- **Innovator** 更强调反事实模拟/MPC 的新意；
- **Contrarian** 则进一步主张：真正重要的不是控制器多聪明，而是**把流量分层和去分布式化作为系统原则**。  
未决问题是：  
**控制器的价值主要来自 smarter scheduling，还是来自更激进的流量治理与拒绝/分流策略？**

# 综合结论：建议保留的 3 条主线

如果要形成一个更有决断力的 proposal，我建议最后就围绕这三条展开：

1. **相位感知动态执行**  
   - 研究对象最“正宗”地属于分布式推理  
   - 易做系统实验  
   - 能产出 workload phase diagram，而不是单点结论

2. **部署感知压缩/蒸馏**  
   - 新意最强  
   - 直接填补 compression 与 distributed serving 的断层  
   - 但必须纳入去分布式化基线比较，防止空转

3. **路径选择优先的在线控制器**  
   - 最现实、最可落地  
   - 也最能回应 contrarian：最优策略可能是少用分布式，而不是更复杂地用分布式

# 不应被“合并掉”的核心争议

最后，最重要的不是把三种视角调和成一致，而是保留这几个真正有研究价值的分歧：

- **分布式推理的未来主线到底是“更聪明地分布式”，还是“尽量避免分布式”？**
- **模型侧优化是否能稳定转化为系统收益，还是大多会被 KV、调度和 tail latency 吞掉？**
- **统一 benchmark 是否真的有意义，还是应该构建 workload family / phase diagram？**
