# Stage 08: Hypothesis Gen

# Core Ideas

## Idea 1: Prefix-/early-representation-aware request scheduling
- One-sentence claim: 用请求前缀相似度或前2–4层轻量表示来分组与重排请求，可在混合在线负载下稳定优于纯 FIFO/长度分桶调度。
- Core novelty: 不是做重型跨层联合优化，而是定义一组低开销、稳定的“模型暴露信号”（prefix overlap、early embedding、KV footprint proxy）供调度器使用，并与传统调度可无缝回退。
- Why it matters: 该机制直接针对 continuous batching 和 KV 复用的真实瓶颈，若有效可在几乎不改模型的前提下同时改善吞吐和尾延迟。
- Minimal validation plan: 在单机多卡推理框架上比较 FIFO、长度分桶、prefix-aware、early-representation-aware 四种调度，在含共享 system prompt、长短混合、多轮对话的回放负载上测 TTFT、token throughput、P95/P99 latency 与调度开销。
- Key risk: 早期表示带来的额外提取与排序开销可能抵消收益，且其增益未必显著超过更简单的 prefix hash。

## Idea 2: Value-aware KV cache retention with selective recomputation
- One-sentence claim: 在线 LLM 服务中，按“未来复用价值”选择性保留 KV、其余摘要化或重算，比默认尽量保留全部 KV 更能降低显存峰值与尾延迟。
- Core novelty: 将 KV cache 从“默认资产”改为“需估值的负债”，基于复用概率、topic drift、retrieval 替换率等廉价信号做价值感知保留，并显式允许“重算优于迁移/保留”。
- Why it matters: 这直接命中长对话、RAG、工具调用场景中的显存碎片、跨卡迁移和 OOM 问题，有机会挑战当前“KV 越多越好”的默认设计。
- Minimal validation plan: 在长对话/RAG混合负载上比较 full retention、滑窗截断、随机/最近淘汰、value-aware retention(+ selective recompute)，测显存峰值、OOM/eviction 次数、P99 latency、吞吐和任务质量下降。
- Key risk: “价值”信号可能不够稳定，导致错误丢弃关键历史，重算成本也可能反过来拉低总体收益。

## Idea 3: Modular online serving beats deeper distributed coordination
- One-sentence claim: 对真实混合在线负载，prefill/decode 解耦 + 少卡副本池 + 条件触发 speculative decoding，可能比统一大池和更深多机协同取得更好的 SLO/成本表现。
- Core novelty: 不再默认“更强分布式协同=更优”，而是把 speculative、并行度和资源池设计都变成按负载条件触发的模块化策略，并用异常守护防止系统振荡。
- Why it matters: 该方向可回答一个关键系统问题：在线推理最优点到底在更深协同还是更强解耦；若结论成立，将显著影响实际服务架构选择。
- Minimal validation plan: 搭建两类对照系统——统一 worker 池/更深模型并行/默认 speculative vs prefill-decode 解耦/少卡副本池/选择性 speculative——在真实或回放混合负载下比较 P95/P99、SLO violation rate、吞吐和单位成本。
- Key risk: 对大模型或高利用率场景，模块化方案可能因资源碎片和副本冗余而输给更强的全局协同。

# Core Ideas

## Idea 1: Risk-aware request isolation for tail-latency control
- Problem gap: Current distributed LLM serving systems mostly optimize average throughput via continuous batching, prefix sharing, and unified schedulers, but they do not explicitly detect and isolate the small fraction of “bad” requests that drive P95/P99 latency under heterogeneous online workloads.
- Core idea: Build a lightweight early-warning model that predicts whether a request will become a tail-latency outlier using features available before or within the first few decode steps: prompt length, estimated prefill FLOPs, prefix-sharing score, first-layer/prefill runtime, first-token entropy, and KV demand estimate. Use this score to route requests into separate queues or worker pools, e.g., low-risk shared batch workers and high-risk isolated workers with stricter admission control, so high-variance jobs stop contaminating normal traffic.
- Why it is new: This is more than length-based bucketing or FIFO; it treats tail requests as a prediction problem and couples prediction with isolation, not just better batching. It also directly tests a contrarian systems hypothesis: simpler selective isolation may beat more complex global co-optimization in real mixed workloads.
- Why it is feasible now: Modern serving stacks like vLLM, TensorRT-LLM, and SGLang already expose request traces, token timings, and cache statistics needed for feature collection. A first version only needs a logistic regression or tiny MLP and can run on 1-4 GPUs without retraining the LLM.
- Minimal experiment: Use ShareGPT-style multi-turn traces plus LongBench-derived long-context prompts to synthesize mixed online workloads; serve Llama-3-8B-Instruct or Qwen2.5-7B-Instruct on vLLM. First implementation step: log per-request early features and train a binary classifier for “will exceed P95 latency under current load.”
- Strong baselines: FIFO queueing; length-based bucketing; standard continuous batching without isolation; shortest-job-first or estimated-prefill-cost scheduling.
- Expected win: Reduce P95/P99 latency by 15-25% for normal requests, while keeping throughput within -5% to +5% of the best unified scheduler; reduce SLA violation rate for short requests.
- Main risk: Early features may be too noisy, so prediction quality is weak and isolation just fragments batches, lowering throughput without enough tail-latency benefit.
- 2-week MVP: Instrument vLLM to collect per-request traces, train a simple bad-request classifier offline, then add a two-queue scheduler: predicted-high-risk requests go to a dedicated worker or capped microbatch, all others use default batching.

## Idea 2: Pressure-aware bounded KV cache instead of maximize-retention
- Problem gap: Most inference systems implicitly treat KV cache retention and sharing as always beneficial, but under multi-tenant distributed workloads this can increase memory pressure, fragmentation, unfairness, and tail latency; prior work rarely tests whether the system optimum is actually below maximum retention.
- Core idea: Replace “keep KV whenever possible” with a bounded cache controller that uses memory pressure, request class, and estimated recompute cost to decide retention, eviction, or selective recomputation. Concretely, maintain per-session KV utility scores based on expected reuse probability, cache size, age/TTL, and short-request interference cost; evict low-utility entries earlier when pressure rises, even if this sacrifices some hit rate.
- Why it is new: The novelty is not another KV compression trick, but reframing cache management as a global service-level tradeoff between hit rate, memory residency, and fairness. This directly challenges the default objective used by many systems baselines, which optimize cache hit ratio rather than end-to-end QoS.
- Why it is feasible now: Existing engines already manage paged KV blocks and expose cache occupancy and token-level timings, so a bounded controller can be implemented as a policy layer without changing model weights. Useful experiments can start on a single node with synthetic multi-session workloads before moving to multi-GPU settings.
- Minimal experiment: Use mixed workloads composed of short chat prompts (ShareGPT), long-context QA (LongBench), and code generation snippets (HumanEval-style prompts) on Llama-3-8B or Qwen2.5-7B with vLLM paged attention. First implementation step: add three KV policies—aggressive keep-all, TTL-bounded retention, and pressure-aware utility eviction—and measure service behavior under increasing concurrency.
- Strong baselines: Default vLLM cache policy; keep-all/prefix-reuse-max policy; TTL-only eviction; LRU-style KV eviction without recompute awareness.

## Hypothesis 1: 风险感知的请求分流/隔离，比更复杂的统一动态协同更能稳定改善尾延迟

### 核心主张
在混合在线负载下，**先用极轻量早期信号识别“坏请求”并做分池/隔离调度**，比把所有请求放进统一的复杂联合优化流水线，更可能带来稳健的 **P95/P99 latency 改善**，且工程复杂度更低。

这融合了：
- innovator 的“异常检测式坏请求预测”
- pragmatist 的“prefill/decode 分离、前缀/请求分组”
- contrarian 的“统一优化未必优于隔离；复杂状态会伤害尾延迟”

### Rationale
主流做法偏向统一 continuous batching、共享缓存、动态路由等全局优化，但真实系统的痛点往往是少数异常请求拖垮尾部。  
因此更强的研究问题不是“怎样让所有请求一起更高效”，而是：

> 能否用廉价的早期特征，把高风险请求提前识别并隔离，从而减少它们对正常请求的干扰？

这比纯长度分桶更新，因为它允许利用：
- prompt length
- prefill 前几层耗时
- attention/logits entropy
- 初始 token 不确定性
- prefix 相似度或长上下文标记

同时，它正面回应 contrarian：  
如果复杂跨层协同真的会放大状态复杂度，那么**风险感知隔离**可能是更高 ROI 的路线。

### Measurable prediction
相对于 FIFO / length-based / 统一 worker：
- 坏请求预测器 AUC ≥ **0.75**
- 风险感知分流使 **P95 或 P99 latency 降低 ≥ 20%**
- 吞吐下降 ≤ **5%**，或持平
- 高风险请求对低风险请求的干扰显著下降
- 在 bursty / heterogeneous 负载下收益大于同质负载

### Failure condition
若出现任一情况，则拒绝该假设：
- AUC < **0.65**
- P95/P99 改善 < **10%**
- 吞吐下降 > **8%**
- 或者统一复杂调度在尾延迟与稳定性上同样更优

### Feasibility
高。  
无需改模型权重，可先在单机或 2–4 GPU 上做：
- 请求特征采集
- logistic regression / 小 MLP 预测坏请求
- 分池调度模拟或真实 serving 原型

## Hypothesis 2: KV cache 不应被默认最大化；“有界保留 + 压力感知驱逐/重算”在分布式混合负载下可能优于激进共享

### 核心主张
在分布式、多租户、长短请求混合场景中，**KV cache 是受约束资源而非天然资产**。  
相较于最大化 cache 保留/共享，采用 **有界 cache、TTL、显存压力感知驱逐，甚至 selective recompute**，可能取得更好的全局 tokens/sec、P99 latency 与公平性。

这融合了：
- innovator 的“不要把 KV 仅看作线性缓存，可结构化裁剪”
- pragmatist 的“调度与缓存协同”
- contrarian 的“KV cache 可能是隐性负债”

### Rationale
大量工作默认“cache 命中越高越好”，但这忽略了：
- 显存挤占与碎片化
- session 粘性和热点
- cache 迁移/跨节点共享成本
- 长会话对短请求的资源霸占
- 命中率提升不等于系统级收益提升

因此最值得检验的不是更复杂的 cache 技巧本身，而是更根本的问题：

> 在真实混合负载中，cache 的系统最优点是否其实低于“尽量保留”？

一个务实版本可以先不做复杂图压缩，而是比较三类策略：
1. 激进保留/共享  
2. 有界 cache + TTL + 压力驱逐  
3. 更激进的 selective recompute / 低保留策略

如果 2/3 赢了，再进一步测试 innovator 的图中心 token 共享是否比简单 TTL 更值。

### Measurable prediction
在多租户混合负载下，相对激进 cache 策略：
- 有界/压力感知策略使 **P99 latency 改善 ≥ 15%**
- 全局 tokens/sec 提升或至少不下降（目标 ≥ **5%**）
- 显存占用峰值或碎片 proxy 降低 ≥ **20%**
- 请求类别间公平性指标改善（如短请求 SLA violation rate 下降）

### Failure condition
若激进 cache 在以下方面都稳定更优，则拒绝该假设：
- 平均吞吐
- P95/P99
- 公平性
- 负载均衡
- 故障恢复/稳定性

或者有界策略导致：
- 吞吐下降 > **10%**
- 质量下降不可接受
- 重算开销显著抵消收益

### Feasibility
中高。  
可先做小规模原型，不必真实多机：
- 单机模拟多会话混合负载
- 控制 cache retention policy
- 记录显存、吞吐、尾延迟、公平性 proxy  
随后再扩展到 2–4 GPU 的 prefll/decode 分离或多 worker 环境。

## Hypothesis 3: 图/结构化方法更适合作为离线策略发现器，而非在线核心决策器

### 核心主张
**图化依赖建模的最佳位置可能是离线，而不是在线 serving 热路径。**  
即：用 attention/请求关系图在离线发现哪些 token、层、请求模式真正关键；在线阶段仅部署蒸馏后的简单规则或轻量分类器。这样的“复杂离线、简单在线”架构，比直接在线跑图策略更稳、更便宜。

这融合了：
- innovator 的两个最有新意想法：  
  - KV 依赖图压缩  
  - 层/请求重要性热图  
- contrarian 的核心批评：  
  - 图方法在线成本和维护风险可能被高估  
- pragmatist 的可落地要求：  
  - 先做 cost model/离线分析，再做轻量上线策略

### Rationale
innovator 的结构化视角是有价值的：它可能揭示简单长度分桶或均匀切分看不到的真实依赖。  
但 contrarian 说得对：在线图构建/图推断很可能不值，尤其在 serving 热路径上。

所以最强综合不是“要不要图方法”，而是：

> 用图方法做策略发现，用简单规则做在线执行。

例如：
- 离线用注意力图找出高影响 token，蒸馏成 top-k/阈值规则
- 离线做层重要性分析，蒸馏成半静态 partition policy
- 在线仅做 hash、查表、线性分类器或固定规则

这保留了新颖性，也直接回答“复杂度是否吞掉收益”的质疑。

### Measurable prediction
相较于两端基线：
- 相比纯简单启发式，离线蒸馏得到的在线轻量策略带来 **≥ 8–15%** 成本/延迟改善
- 相比在线图策略，其收益接近（保留 **≥ 80–90%** 的收益）
- 但在线开销显著更低，P99 更稳定

这里“成本/延迟改善”可以具体化为：
- KV 共享量下降
- 分片 cost model 改善
- 通信+计算总成本下降
- 或 tail latency 改善

### Failure condition
若出现以下情况则拒绝：
- 离线图发现无法蒸馏成简单在线规则
- 轻量在线策略相对启发式提升 < **5%**
- 在线图策略在真实负载中开销可接受且明显更优  
  （说明 contrarian 的担心不成立）

### Feasibility
中等。  
最适合做成两阶段原型：
1. 单卡离线分析 attention/layer 重要性  
2. 用蒸馏后的规则在 serving 模拟器或小规模多 worker 环境中验证

# 未解决的分歧

以下分歧不应被抹平，反而应作为研究设计的一部分：

1. **统一协同 vs 专用隔离**
   - innovator 倾向跨层联合优化
   - contrarian 认为统一系统可能天然次优
   - 当前综合判断：先检验“风险感知隔离”是否比统一复杂协同更稳健，而不是预设某一方正确

2. **KV cache 是资产还是负债**
   - pragmatist 默认 cache/prefix reuse 常常有益
   - contrarian 认为在分布式混合负载下可能反转
   - 当前综合判断：必须把公平性、碎片化、尾延迟纳入评价，而不只看命中率和平均吞吐

3. **图方法应在线还是离线**
   - innovator 强调结构化建模的新价值
   - contrarian 质疑在线部署 ROI
   - 当前综合判断：优先测试“离线发现 + 在线轻执行”，这是双方最有可能被证伪也最可落地的交点
